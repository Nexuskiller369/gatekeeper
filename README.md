# Gatekeeper: access control for NFPL customs jobs

A service that decides **who may do what on which job**, explains every answer, shows each
person the jobs that need them, and keeps a history that can answer "who did this, under what
authority, and who *could* have done it on the 3rd?"

- **Design document:** [docs/DESIGN.md](docs/DESIGN.md) covers the model, the trade-offs, and answers to all 14 questions.
- **Plain-language guide:** [docs/GUIDE.md](docs/GUIDE.md) covers how everything fits together, in basic terms.

Stack: Node.js 22+, TypeScript, Express 5, Prisma 6, PostgreSQL 16 (Docker), Vitest + Supertest.

## 1. Run it locally

Prerequisites: Node.js 22+, Docker Desktop (running), Git Bash or PowerShell.

```bash
npm install
cp .env.example .env              # PowerShell: Copy-Item .env.example .env
                                  # then set JWT_SECRET to any long random string
npm run db:up                     # Postgres on localhost:5433 (+ an empty gatekeeper_test DB)
npx prisma migrate deploy         # create the tables
npm run seed                      # load the sample data (one command, re-runnable)
npm run dev                       # http://localhost:3000
```

Check it: `curl http://localhost:3000/health` should return `{"status":"ok"}`.

Every human user's password is **`Password123!`**. Emails are `<id>@nfpl.test`, for example `sarah@nfpl.test`.

### All commands

| Command | What it does |
|---|---|
| `npm run dev` / `npm start` | Start the API (dev mode reloads on file changes) |
| `npm run seed` | Wipe and reload the sample data |
| `npm test` | Run all tests (unit + integration, against the separate `gatekeeper_test` DB) |
| `npm run parser:run [file]` | Run the overnight parser (default `data/parser/sample-shipments.json`; `.csv` also works) |
| `npm run access:describe [userId]` | Print everyone's access in plain English |
| `npm run seed:scale [-- --jobs N]` | Generate the scale case (500 users, 200,000 jobs) in a **separate** `gatekeeper_scale` DB |
| `npm run build` | Type-check |
| `npm run db:down` | Stop Postgres |

## 3. API

Log in, then send the token as `Authorization: Bearer <token>` on every other call.
The token carries **only the user id**. Roles are read from the database on every request, so a
revoke or deactivation takes effect on the next request, not when the token expires.

| Method & path | Purpose | Who |
|---|---|---|
| `POST /auth/login` `{email,password}` | Get a token | anyone |
| `GET /auth/me` | My access, in plain English | anyone logged in |
| `GET /jobs?stage=&clientId=&branchId=&direction=&mode=&assigneeId=&cursor=&limit=` | Jobs I can see (filtered in SQL, paginated) | anyone with `job.view` |
| `GET /jobs/waiting-for-me` | Jobs whose next step I can actually perform now | anyone |
| `GET /jobs/:id` | One job + `allowedActions` for me (id or reference) | `job.view` |
| `PATCH /jobs/:id` `{consignee?,weightKg?,valueInr?,notes?}` | Edit business data (only CONFIRMED/REOPENED) | MAKER |
| `POST /jobs/:id/prepare` · `check` · `file` | Workflow steps | MAKER · CHECKER · FILER |
| `POST /jobs/:id/reject` `{reason}` | Checker sends it back | CHECKER |
| `POST /jobs/:id/cancel` `{reason}` | Cancel (a filed job needs `job.cancel_filed`) | MAKER / OPS_ADMIN |
| `POST /jobs/:id/reopen` `{reason}` | Reopen a filed/cancelled job | OPS_ADMIN |
| `POST /jobs/:id/assign` `{assigneeId,reason}` | Reassign a stuck job (only to someone eligible) | OPS_ADMIN |
| `GET /jobs/:id/history` | Who did what, when, under which grant/delegation | `job.view`, or auditors |
| `POST /authorization/check` `{action,jobId,userIds?,at?}` | **"Why can she and he can't?"**: a decision + reasoning trace per user, optionally at a past time | self; others need `access.explain` |
| `GET /jobs/:id/who-could-act?at=&action=` | **"Who could have changed this job on the 3rd?"** | `access.explain` / `audit.view` |
| `GET /access-grants?userId=` · `POST /access-grants` · `POST /access-grants/:id/revoke` | Manage grants (reason required) | ACCESS_ADMIN |
| `GET /delegations` · `POST /delegations` · `POST /delegations/:id/revoke` | Temporary cover | ACCESS_ADMIN |
| `POST /users/:id/absences` `{startsAt,endsAt,reason}` | Mark someone absent (their open work is re-routed) | ACCESS_ADMIN |
| `PATCH /users/:id/status` `{status,reason}` | Activate/deactivate | ACCESS_ADMIN |
| `GET /users` · `GET /roles` | Users with their access; role catalogue | ACCESS_ADMIN / anyone |
| `GET /audit/access` · `GET /audit/automation?jobId=` | Access-change audit (incl. denied attempts); automation/parser log | `audit.view` |

Errors look like `{"error":{"code":"SOD_VIOLATION","message":"...","details":{"decision":{...}}}}`.
`401` means not logged in. `403` means logged in but not allowed (with the reason). `404` is also used when you're
not allowed to *see* a job, so its existence isn't revealed. `409` means someone changed the job first.

## 4. Five-minute demo

Run these in Git Bash with the server running and fresh seed data (`npm run seed`).

```bash
B=http://localhost:3000
tok() { curl -s -X POST $B/auth/login -H 'content-type: application/json' \
  -d "{\"email\":\"$1@nfpl.test\",\"password\":\"Password123!\"}" | sed -E 's/.*"token":"([^"]+)".*/\1/'; }
ANITA=$(tok anita); RAJ=$(tok raj); SARAH=$(tok sarah); FIONA=$(tok fiona); OMAR=$(tok omar); TOM=$(tok tom)

# 1. Who am I?  (plain-English access)
curl -s $B/auth/me -H "authorization: Bearer $SARAH"

# 2. "Why can she do this and he can't?"  Sarah vs Raj vs Alice on NF-DEMO-03 (ACME / DEL / EXPORT)
curl -s -X POST $B/authorization/check -H "authorization: Bearer $ANITA" -H 'content-type: application/json' \
  -d '{"action":"job.check","jobId":"NF-DEMO-03","userIds":["sarah","raj","alice"]}'
#    sarah -> ALLOW (CHECKER for ACME covers it)
#    raj   -> DENY SCOPE_MISMATCH (his grant is BOM + IMPORT only)
#    alice -> DENY NO_PERMISSION (she has no CHECKER role at all)
#    each decision carries a step-by-step "trace" of the checks that ran

# 3. Maker-checker: Sarah prepared NF-DEMO-02, so she can't check it
curl -s -X POST $B/jobs/NF-DEMO-02/check -H "authorization: Bearer $SARAH"     # 403 SOD_VIOLATION
curl -s -X POST $B/jobs/NF-DEMO-02/check -H "authorization: Bearer $RAJ"       # 200, CHECKED
curl -s -X POST $B/jobs/NF-DEMO-02/file  -H "authorization: Bearer $FIONA"     # 200, FILED

# 4. The incident: nobody can quietly alter a filed job
curl -s -X PATCH $B/jobs/NF-DEMO-04 -H "authorization: Bearer $SARAH" -H 'content-type: application/json' -d '{"notes":"x"}'  # 403 FILED_LOCKED
curl -s -X POST $B/jobs/NF-DEMO-04/cancel -H "authorization: Bearer $OMAR" -H 'content-type: application/json' -d '{"reason":"Duplicate filing"}'  # 200

# 5. A job's history: who did what, under which grant
curl -s $B/jobs/NF-DEMO-04/history -H "authorization: Bearer $ANITA"

# 6. "Who could have changed this job on the 3rd?"
curl -s "$B/jobs/NF-DEMO-04/who-could-act?at=2026-11-03T12:00:00Z" -H "authorization: Bearer $ANITA"

# 7. Jobs waiting for me; client users see only their own shipments
curl -s "$B/jobs/waiting-for-me" -H "authorization: Bearer $RAJ"
curl -s "$B/jobs?limit=5" -H "authorization: Bearer $TOM"

# 8. An admin trying to make themselves more powerful (denied AND audited)
curl -s -X POST $B/access-grants -H "authorization: Bearer $ANITA" -H 'content-type: application/json' \
  -d '{"userId":"anita","roleId":"FILER","reason":"I want to file"}'                # 403 SELF_ESCALATION
curl -s "$B/audit/access?limit=1" -H "authorization: Bearer $ANITA"

# 9. The overnight parser (run it twice: the second run changes nothing)
npm run parser:run
```

> Seed dates are relative to when you ran `npm run seed`. For step 6, pick a time after the job was filed. `GET /jobs/NF-DEMO-04/history` shows the timestamps.

## 5. Tests

```bash
npm test
```

65 tests: **33 unit tests** on the pure decision engine, plus **32 integration tests** that go
through HTTP → services → engine → a real Postgres test database, with nothing in the authorization path
mocked. They cover maker/checker conflict, scope mismatches (client, branch, direction), absence,
delegation (valid, out of scope, expired), filed-job lock, cancel/reopen with reason, an admin who filed
the job being blocked, admin self-escalation, a branch admin granting outside their branch, grants and revokes
taking effect immediately, **changed responsibility** (revoke mid-job → work re-routed), historical
access ("as of" a past date), waiting-for-me agreeing with the engine, routing excluding the
preparer, absence re-routing never picking an unauthorized person, the parser (create, update, locked,
idempotent re-run), concurrent double-check (exactly one wins), and authentication.

Tests run against `gatekeeper_test` (created automatically by `npm run db:up`), never your demo data.

## 6. Overnight parser

```bash
npm run parser:run                                     # data/parser/sample-shipments.json
npm run parser:run -- data/parser/sample-shipments.csv
```

Runs as the `parser` service identity through the same engine as people. For each record:
**CREATED** (new `externalRef`), **UPDATED** (imported fields changed, job not yet prepared),
**UNCHANGED** (same data, so re-running is safe), **REJECTED** (e.g. job already prepared or filed, unknown
client, or the feed tried to change client/branch/direction/mode, which decide access), or **INVALID**
(bad shape). One bad record never stops the batch. Every outcome is logged (`GET /audit/automation`).

## 7. Scale case (500 users, 200,000 jobs)

```bash
npm run seed:scale                  # full size, about 2 minutes
npm run seed:scale -- --jobs 20000  # quicker
```

This writes to a **separate database** (`gatekeeper_scale`, or `SCALE_DATABASE_URL`), so demo data and
tests are untouched. It uses batched `createMany` inserts, then runs `ANALYZE`, prints row counts, and times real
service calls. One measured run on the author's laptop (single run, not a benchmark):

| | |
|---|---|
| Generated | 500 users, 200,008 jobs, 667,319 history rows in 110 s |
| `GET /jobs` first page (scoped checker / global viewer / client user) | 35 / 25 / 15 ms |
| Waiting-for-me (3-branch checker / global filer) | 62 / 16 ms |
| Job history | 8 ms |
| Who-could-act (engine over all 500 users) | 44 ms |

Verify it yourself:

```bash
docker exec -it gatekeeper-postgres psql -U gatekeeper -d gatekeeper_scale -c 'SELECT stage, count(*) FROM "Job" GROUP BY 1'
```

To point the API at it, temporarily set `DATABASE_URL` to the `gatekeeper_scale` database.

## 8. What was cut, and why

The brief says "cut scope if you must, but tell us." With a 4–6 hour budget I prioritized the
decision engine, explanations, history and tests over breadth.

| Cut | Why | What exists instead |
|---|---|---|
| Configurable automation-rule engine, event bus | Big surface, little extra proof of access-control thinking | Routing and re-routing run synchronously after each change, in one service |
| Overdue-job escalation, notifications | Depend on the rule engine above | Documented as next steps; not claimed as built |
| Admin API to create new roles | Roles are already data (a table row with a permission list) | New role = one row, no code change (see DESIGN Q12) |
| Parser HTTP endpoint | The parser is a batch job, not a user | CLI that runs as the parser identity |
| Self-registration, Postman collection, UI | Not needed to judge the core | curl demo above |

## 9. Project layout

```
src/
  authz/engine.ts         the decision engine: pure functions, no DB (decide, decideAccessChange)
  authz/context.ts        loads the facts the engine needs (user, grants, delegations, absences, job history)
  authz/scope.ts          "does this grant's scope cover this job?"
  authz/describe.ts       turns grants into plain-English sentences
  domain/permissions.ts   permission catalogue, stage rules, separation-of-duties rules
  services/               jobs, queue (waiting-for-me), routing, access admin, history/explain, parser
  http/                   auth (JWT), routes (thin), errors
  seed/seed.ts            the sample data
scripts/                  runParser, describeAccess, generateScaleData
prisma/schema.prisma      data model + indexes
tests/unit, tests/integration
docs/DESIGN.md, docs/GUIDE.md
```

## 10. Troubleshooting

| Problem | Fix |
|---|---|
| `Can't reach database server at localhost:5433` | Start Docker Desktop, then `npm run db:up` |
| `Missing required environment variable JWT_SECRET` | `cp .env.example .env` and set a value |
| Tests fail with "database gatekeeper_test does not exist" | The volume predates the init script: `npm run db:down`, `docker volume rm gatekeeper_gatekeeper-pgdata`, then `npm run db:up` |
| Port 3000 in use | Set `PORT=3001` in `.env` |
| A token "stopped working" | Expected if the user was deactivated; log in again |
